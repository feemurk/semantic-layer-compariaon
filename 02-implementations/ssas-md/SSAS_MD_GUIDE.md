# S1 — SSAS Multidimensional

Stack S1 of SPEC § 3.1: one SQL Server 2025 Analysis Services Multidimensional database (`slc`, cubes `WWI` and `NYC`) over the shared Databricks gold tables. It serves the 22 metrics and 70 questions through MDX, with no model change between questions.

## 2. Model structure

### 2.1 Connectivity: the SQL Server adapter

SPEC § 3.1 specified an ODBC data source over Databricks. The supported-data-sources page rules it out on two counts: ODBC data sources are not supported for multidimensional solutions, and ROLAP storage requires a SQL Server relational source. The model therefore reads Databricks through SQL Server 2025:

| Hop | Component | Configuration |
|---|---|---|
| Databricks serverless SQL → SQL Server 2025 | PolyBase ODBC-generic external data source `slc_databricks`, Databricks ODBC Driver (`AuthMech=3`, `PUSHDOWN = ON`) | [adapter/01_polybase.sql](adapter/01_polybase.sql) |
| Gold tables in SQL Server | 14 external tables `wwi.*`, `nyctaxi.*`, `LOCATION = 'slc.<schema>.<table>'`, generated from the canonical schema | [adapter/02_external_tables.sql](adapter/02_external_tables.sql) |
| SQL Server → SSAS | Relational data source `slc_adapter`, provider `MSOLEDBSQL`, service-account impersonation | [model/slc.ds](model/slc.ds) |

Data stays in Databricks (SPEC D-08). MOLAP processing and ROLAP queries are SQL statements against external tables, pushed down to the SQL warehouse. The adapter is the stack's largest boundary (B-09, § 8).

### 2.2 Dimensions

| Database dimension | Cube roles | Key | Attributes and hierarchies |
|---|---|---|---|
| Date | Date (invoice, order and snapshot date), Delivery Date | `date_id` (yyyymmdd) | Calendar (Year › Quarter › Month › Date), Fiscal (Fiscal Year › Fiscal Quarter › Fiscal Month › Date); Month Of Year, Quarter Of Year, Fiscal Month/Quarter Of Year; Month End Date and Quarter End Date as member properties |
| Customer | Customer, Bill To Customer | `customer_key` | Customer (keyed by name), Category, Buying Group |
| City | City | `city_key` | Geography (Continent › Country › State Province › City), Territory (Sales Territory › State Province › City); City keyed by (state, city) |
| Stock Item | Stock Item | `stock_item_key` | WWI Stock Item ID (durable) with Stock Item, Current Color, Selling Package, Is Chiller Stock, Balance Basis; Color, Brand, Size on the version |
| Stock Group | Stock Group | `stock_group_id` | Stock Group |
| Employee | Salesperson, Picker | `employee_key` | Employee (keyed by name) |
| Inventory Access | Inventory Access | constant 1 | Security device (§ 4) |
| NYC Date | Pickup Date, Dropoff Date | `date_id` | Calendar (Year › Quarter › Month › Date); Month Of Year, Day Of Week, Day Name; properties Day Of Month, Day Of Year, STLY Date ID; In Source Window |
| Zone | Pickup Zone, Dropoff Zone | `location_id` | Zones (Borough › Zone); Location ID, Service Zone |
| Payment Type | Payment Type | `payment_type` | Payment Type Code, Payment Type (label) |
| Vendor, Pickup Hour | same | code | single attribute |

Patterns:

- **Role-playing dimensions** are cube dimensions over one database dimension. The single cube dimension Date binds `invoice_date`, `order_date` and `snapshot_date`, so one Date selection filters sales, orders and stock together (W-S2).
- **SCD2, as-was and as-is.** Facts relate on surrogate keys, so Color is as-was. Current Color comes from the version with `is_current = 1` of the same durable item, through the DSV named query, and hangs off WWI Stock Item ID (Q-W-S1-D4). Attributes keyed by name (Customer, Employee, Stock Item) aggregate all versions of one entity into one member, matching the oracle's grouping by label.
- **Attribute relationships** form natural hierarchies (`lint_mdx.py` checks each level reaches its parent), so aggregations and autoexists follow rigid functional dependencies. The fixture layer of the test suite verifies those dependencies on data.
- **Captions equal oracle labels.** Name columns are text built in the DSV (ISO dates, year strings, `true`/`false`), so a flattened cell set compares to the oracle without conversion.
- **Agent metadata.** Glossary descriptions become `Description` on cube dimensions, stored measures and calculated measures (`CalculationProperty`). Synonyms become `slc:synonyms` annotations, because ASSL has no synonym property; the agent harness reads both through discovery rowsets.

### 2.3 Cubes and measure groups

| Cube | Measure group | Source | Measures | Notes |
|---|---|---|---|---|
| WWI | Sales | `wwi_sales` | Revenue, Revenue Including Tax, Gross Profit, Units Sold | Delivery Date and Picker unrelated |
| WWI | Invoices | `wwi_sales` | Invoice Count (DistinctCount) | Dedicated group (B-06) |
| WWI | Orders | `wwi_orders` | Ordered Quantity | Picker with unknown member for NULL keys |
| WWI | Backorders | `wwi_backorders` | Backordered Order Lines (row count) | Only lines with a backorder id, so an empty cell is NULL, not 0 |
| WWI | Stock Holdings | `wwi_stock_holding` | Closing Units (LastNonEmpty) | Dense daily snapshot; related to Date, Stock Item, Stock Group, Inventory Access only |
| WWI | Stock Item Group Bridge | `wwi_stock_item_group` | (hidden count) | Intermediate group; relates to Stock Item at the durable WWI Stock Item ID |
| NYC | Trips | `nyc_trips` | Trip Count, Total Trip Distance, Fare/Tip/Tolls Amount, Gross Trip Revenue | 24 monthly MOLAP partitions + ROLAP hot partition |
| NYC | OD Pairs | `nyc_trips` | Distinct OD Pairs (DistinctCount) | Dedicated group (B-06), same partition scheme |

Every measure group has `IgnoreUnrelatedDimensions = false`, so a dimension that does not apply to a metric returns NULL (SPEC § 6.5). Stock Group is a many-to-many dimension of every WWI fact group through the bridge.

## 3. Calculation semantics

Calculated measures are in [mdx/WWI.mdx](mdx/WWI.mdx) and [mdx/NYC.mdx](mdx/NYC.mdx).

| Metric | Mechanism |
|---|---|
| Additive (B-W1–B-W3, W-S1, W-S2, B-N1–B-N5, N-S1) | Stored `Sum` / `Count` measures |
| Distinct counts (B-W4, N-M1) | `DistinctCount` in dedicated measure groups, exact |
| B-W5 | Row count of a measure group filtered to backordered lines |
| N-S2 Card Tips | Additive `card_tip` and `card_trip` columns; `IIF(Card Trips = 0, NULL, Card Tips Sum)` returns NULL for every payment type except 1 |
| Ratios (W-M1, N-M2) | Calculated measures over the aggregated sums, `NULL` on a zero or empty denominator |
| W-M2 | `LastNonEmpty` over the dense snapshot: the last snapshot date in the period, capped at 2016-05-31 because no later rows exist |
| W-C1 | The many-to-many relationship deduplicates every total across groups, so the All member of Stock Group equals W-S1. Share is `Revenue / (Revenue, [Stock Group].[All])` and is 1 at any total. |
| W-C2 | `Units Sold 91D = Sum(LastPeriods(91, anchor), Units Sold)`, where the anchor is the last non-empty snapshot date in `EXISTING` date context. Assigning the Date attribute overwrites the period attributes, so the window ignores the period's lower bound; Stock Item and Stock Group filters stay in force. A non-conformed dimension leaves Closing Units empty, which returns NULL. |
| N-C1 | Anchor `t(P)` = last date of the Pickup Date period in context within the source window (`In Source Window`), as SPEC § 6.1 defines it. `Revenue YTD = Sum(PeriodsToDate(Year, anchor))`. The STLY anchor is the `STLY Date ID` member property (29 February → 28 February) resolved with `StrToMember`. |
| N-C2 | Trips MTD/YTD with `PeriodsToDate` at Month and Year; Day Of Month and Day Of Year properties of the anchor give calendar days elapsed |

Points of difference from S4:

- **Calendar anchor.** S1 anchors period-to-date metrics on the calendar end of the period whether or not the member has data that day. That is the SPEC definition, so the S4 boundary B-07 (anchor on the last date with data) does not occur here.
- **ParallelPeriod is not used for STLY.** It returns the member "in the same relative position", so in a leap year every date after 28 February maps to the next day of the prior year (2024-03-01 → 2023-03-02). A key-based property mapping gives the SPEC rule.
- **Members exist independently of facts.** An MDX axis can list dimension members without facts. Q-W-S2-P returns all twelve 2015 months and Q-N-S2-D4 all seven payment types, as the oracle does, so S4's boundary B-08 does not occur here. Queries use `NonEmpty` only where the oracle lists members through facts.
- **Dropoff Date and period metrics.** `SCOPE` assignments set the N-C1 and N-C2 measures to NULL for any Dropoff Date member below All (SPEC § 6.5).

## 4. Security model

Roles ([model/](model/)`*.role`, cube permissions in [model/WWI.cube](model/WWI.cube) and [model/NYC.cube](model/NYC.cube)):

| Role | Members (rewritten per environment by `deploy.ps1 -RoleDomain`) | Cube permissions |
|---|---|---|
| SLC Analysts | `SLC\slc_analysts` | Read on WWI and NYC |
| Territory Analyst - Southeast | `SLC\slc_territory_southeast` | WWI: City.Sales Territory allowed set `{[City].[Sales Territory].&[Southeast]}`; Inventory Access allowed set `{}`; both with visual totals. No NYC access |
| Manhattan Pickup Analyst | `SLC\slc_pickup_manhattan` | NYC: Pickup Zone.Borough allowed set `{[Pickup Zone].[Borough].&[Manhattan]}` with visual totals; Dropoff Zone unrestricted. No WWI access |

- Dimension data security on the City cube dimension restricts every sales and order measure by the as-was city, because both facts relate through `city_key`.
- Visual totals recalculate the All member from the allowed members only. Without them, totals would still show unrestricted values.
- **No inventory access.** Inventory Access relates only to Stock Holdings, so the empty allowed set with visual totals empties Closing Units, and Days of Supply follows. Sales and orders are unaffected because they are unrelated to that dimension. That an empty allowed set with visual totals yields NULL rather than an access error is pending verification (V-NEW-5).
- Role-playing makes the NYC rule precise: the permission is on the Pickup Zone cube dimension, so the Dropoff Zone role of the same database dimension stays open.

## 5. Performance behavior

- **Storage.** WWI measure groups are single MOLAP partitions. NYC Trips and OD Pairs have one MOLAP partition per pickup month (24) plus a ROLAP hot partition from the first unclosed month. Distinct count partitioning by month keeps each distinct-count scan to one month's segment.
- **Edition.** Enterprise edition is required: LastNonEmpty is not in Standard (LastChild only), and Standard allows at most 3 partitions per measure group.
- **Freshness (E4).** The hot partition reads the adapter on every query, so new gold rows are visible once the Databricks pipeline commits them. Real-time ROLAP would need change notifications from the relational source, which PolyBase external tables cannot raise. The freshness poller therefore issues `ClearCache` on the hot measure groups before each probe ([jobs/partition_rollover.py](jobs/partition_rollover.py) emits the command).
- **Aggregations.** No aggregation designs ship with the model. They are designed after the E3 baseline from the query log (usage-based optimization) and committed to `build_model.py`.
- **Formula engine.** The W-C2 and N-C1/N-C2 calculations evaluate `EXISTING` date sets per cell, and N-C1 uses `StrToMember`. These are the most expensive cells in the model, and E3 measures them at concurrency 1 and 10.
- **Timings.** `scripts/reconcile.ps1 -Repeat n` records cold and warm timings per statement in `timings.json`.

## 6. Deployment, refresh and CI/CD

| Step | Command |
|---|---|
| Adapter, model, process | `scripts/deploy.ps1 -SsasServer <ssas> -SqlServer <sql>`: runs the adapter scripts with sqlcmd variables from environment variables, rewrites the data source and role members for the environment, then sends `deploy/slc.xmla` and `deploy/process_full.xmla` with `Invoke-ASCmd` |
| Monthly rollover (E6) | `scripts/rollover.ps1 -CloseMonth YYYY-MM`: reads the partition list (`DISCOVER_XML_METADATA`), then runs one transactional batch that creates and processes the closed month, re-slices the hot partition and deletes months beyond 24, followed by `ClearCache` |
| Reconciliation (E1, E2) | `scripts/reconcile.ps1 [-Select glob] [-Repeat n] [-FailOnMismatch]` (§ 7) |

The rollover plan is computed from the current partitions, so a rerun after a failure resumes without duplicating work. Partitions are never merged: retention is monthly, and a merged partition could not be retired one month at a time.

[s1-ssas-md.yml](../../.github/workflows/s1-ssas-md.yml) runs on every push touching this stack, the oracle answers or the glossary:

1. `lint` (GitHub-hosted): both builders with `--check`, `lint_mdx.py`, and the test suite.
2. `test`: a self-hosted Windows runner (label `slc-ssas`), environment `test`, runs `deploy.ps1`, then `reconcile.ps1 -Select 'Q-*-P' -FailOnMismatch`.
3. `promote`: the same on `main`, environment `prod`.

Secrets (`DATABRICKS_TOKEN`, `ADAPTER_MASTER_KEY_PASSWORD`) live in the GitHub environments and reach SQL Server only as sqlcmd variables.

## 7. Verification

Flattening rules applied by `reconcile.ps1`:

- **Metric files** are statements preceded by `// @branch grain=… rows=… values=label:[Measures].[M],…`. Each row tuple and value gives one contract row, with `member_i` the caption on the i-th declared row hierarchy.
- **Question files** declare `// @column name = source`, where the source is a row hierarchy (its caption) or a measure on the COLUMNS axis (its value).
- An All member flattens to NULL. Numbers use the invariant culture, and doubles round-trip.
- `tools/compare.py` compares metrics keyed under SPEC § 5.3 rule 7 (an absent row equals NULL; the labels NULL, blank and `Unknown` are equivalent) and questions as row multisets under § 9.3 tolerances.

| Layer | Evidence |
|---|---|
| Documentation | URLs above, checked 2026-11-20 |
| ASSL | All model files and the deploy command are well-formed; every binding, relationship, natural hierarchy, cube dimension, measure group and permission resolves (`lint_mdx.py`) |
| Relational layer | Every DSV named query runs on DuckDB 1.4.1 over the oracle fixtures and returns its declared columns. Dimension keys are unique, every attribute relationship holds as a functional dependency, every fact key resolves to a member, and monthly partitions are disjoint and cover every trip. |
| MDX | All 92 query files and both scripts resolve every hierarchy, level, measure and member property. `@column` and `@branch` declarations match the oracle headers, grains and measure labels. |
| Operations | Rollover plans for two consecutive months; transactional XMLA; comparator positives and negatives |
| SSAS execution | Not performed: no SQL Server 2025 instance in this environment. E1, E2, E3 and E8 run with `deploy.ps1` and `reconcile.ps1` on the Windows runner. |

The DSV SQL is written in the ANSI subset that SQL Server and DuckDB share: CAST to integer before key arithmetic, CONCAT, correlated subqueries, no dialect date functions. DuckDB is a proxy for T-SQL, not SQL Server itself.

## 8. Limitations and boundaries

| ID | Boundary | Consequence in S1 | Workaround and cost |
|---|---|---|---|
| B-04 | No native natural-language assistant | No lane A for S1 (SPEC § 11.1) | Common MCP harness over XMLA only |
| B-06 | Distinct counts need a dedicated measure group | Invoices and OD Pairs measure groups duplicate their fact's dimension usage | Two extra measure groups and their partitions; confirmed by design |
| B-09 (proposed) | Multidimensional has no supported Databricks connection: ODBC is unsupported, and ROLAP requires SQL Server | A SQL Server 2025 instance with PolyBase sits between Databricks and SSAS | One more server, a credential, 14 external tables, and a second hop on ROLAP queries |
| B-10 (proposed) | Real-time ROLAP depends on relational change notifications | External tables cannot notify, so the hot partition's cache must be cleared by the poller | `ClearCache` before each freshness probe; E4 latency includes the clear |
| — | Enterprise edition | Standard caps partitions at 3 and offers LastChild only | Licensing |

Further limits:

- **Restricted reconciliation.** The oracle does not yet carry restricted expected answers per role (SPEC § 10), so E8 cannot be scored.
- **Prerequisites outside the repository:**
  - a SQL Server 2025 instance (`slc-sql2025` by default) with PolyBase and the Databricks ODBC Driver;
  - an SSAS 2025 instance in Multidimensional mode, Enterprise edition;
  - the Windows groups behind the three roles;
  - a self-hosted runner labeled `slc-ssas`.
- **Pending verification** (reported for the SPEC register):
  - PolyBase ODBC-generic with the Databricks ODBC driver and three-part `LOCATION` names;
  - visual totals with an empty allowed set returning NULL;
  - the ASSL element order accepted by the 2025 engine;
  - `ClearCache` making ROLAP results current.
